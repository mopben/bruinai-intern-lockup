# Decision log

Short entries: what we chose and why. Append under your own heading.

## Orchestrator

- **One TypeScript codebase, simulation in the browser.** A drag must answer with no visible wait and the demo must run offline. A Python service would add a process, a network hop and a second language for no gain.
- **Camera tracking by hat colour, in the browser.** The run is staged: high fixed camera, three or four people, each in a different coloured hat. Colour blobs are simpler and more reliable there than a person detector, need no model download, and can be tested on a synthetic video. The filming phone acts as the laptop's webcam.
- **RoomPlan is used for the scan only.** It captures room geometry and has no people tracking, so it cannot supply positions.
- **Fixtures come from a separate world generator** (`tools/world/`), which never shares parameters with the model. Otherwise the trust check and the prediction test would be the model agreeing with itself.
- **Trust check on held-out orders.** Calibrate on even-numbered orders, score on odd-numbered ones. Interleaving avoids confusing drift (people speed up) with model error.
- **Three recorded runs**: original, fridge moved closer, fourth worker. Whichever change a judge picks, a recorded run exists to test the prediction against.
- **The brief wins over the team summary where they differ.** The close is the side-by-side run, not a slide. Level 1 uses a recorded scan, not a hand-built kitchen.
- **`npm start` installs and builds on first run.** That first run needs internet; the demo does not. Committing build output to avoid this was judged worse.
- **The stage is the run clock.** It releases orders and stamps taps on receipt, so device clocks never need to agree.

## Scan app (iOS)

- **The app maps RoomPlan output to our `Scan` itself**, in a pure function with unit tests. We do not ship RoomPlan's own JSON, because its shape cannot be checked without a device.
- **Walls get a nominal thickness of 0.1 m.** RoomPlan walls have none.
- **No re-centring.** x and z stay in the phone's frame, with the origin where the scan started. Nothing downstream needs a centred scan: the scene frames whatever it is given, and positions use the same frame.
- **Categories are RoomPlan's own case names** (`table`, `storage`, `refrigerator`, `washerDryer`). An unknown case becomes `unknown`.
- **Doors, windows, openings and wall curvature are skipped.** The model does not use them.
- **Unknown until a real scan exists:** which side RoomPlan treats as an object's front. The owner can set the stand side in the stage app.

## Core

- **Yaw follows three.js.** Local (x, z) maps to world as x' = x cos(yaw) + z sin(yaw), z' = -x sin(yaw) + z cos(yaw), the same as `object.rotation.y = yaw`. `standSide` "left" is local -x and "right" is local +x (left and right as the viewer sees a yaw-0 box).
- **Grown obstacles have square corners.** Boxes and walls are grown by BODY_RADIUS_M as rectangles, not rounded rectangles, so the visibility graph is over four corners each. This overstates a detour round a corner by at most about 0.1 m (r(√2-1) per corner side). Exact for the model we state; slightly conservative against a real body.
- **Stand points and margins.** STAND_OFF_M (0.35) is larger than BODY_RADIUS_M (0.25), so a stand point is outside its own box's margin. It can still fall inside a neighbour's or a wall's margin. Rule: for one path query, an obstacle whose grown rectangle contains either end point is replaced by its un-grown box (step out of the margin, never through the box); if an end point is inside the box itself, that obstacle is ignored for the query. Gaps exactly one body wide are walkable.
- **No path is not an error.** It returns a straight line with `blocked: true`, so a drag into a corner never throws; the UI should say "no way through".
- **Hand-off uses the straight line** between stand points (≤ HANDOFF_REACH_M, inclusive), even if a wall is in between. Fetches are always walked.
- **Scanned boxes with no setup entry are fixtures** (they block walking) with a warning, rather than an error, so a fresh scan resolves before the owner has named everything.
- **Messy tap logs: a step is done at the earliest tap of itself or any later step.** A later step being done proves the earlier one was. Duplicates keep the first tap. Unknown orders/steps and taps before release are ignored with a warning. Releases come from order events; an order with taps but no order event takes its scheduled time; a log with no order events uses the schedule up to the end of the run.
- **Ticket semantics.** A ticket sits at station k from when step k-1 was done (or release) until step k is done, in both recorded and simulated runs, so they animate the same. In the simulation the item physically arrives after the carry walk; the ticket counts as "at" the next station during the carry.
- **Calibration speed.** Displacement over 0.5 s windows (beats position noise), windows faster than 0.4 m/s count as walking, median across all workers. Fewer than 5 walking windows: assume 1.2 m/s and say so. These thresholds were set before any fixture existed and are not tuned to them. Speed is not bootstrapped (hundreds of windows make it precise); only work times are.
- **Work-time samples = tap - max(arrival, worker free) - fetch walk**, where arrival = previous tap + one-way carry, worker free = their previous tap at this station + carry round trip. Only clean steps are sampled (this and the previous step tapped, in sequence). With several workers at a station and no workerId in the log, the step is given to the worker free earliest. Samples below 0.5 s are raised to 0.5 s and counted. A missing tap leaves the worker-free time stale (it can inflate the next sample); we accept that rather than guess.
- **Trust check: the filter applies to samples, not to queue state.** Calibrating on even orders still uses odd orders' taps to know when a worker became free (otherwise queue waiting would be counted as work), and the speed comes from the whole position log. Neither fits the model to the odd orders' order times, which are only compared, never learned from. Error is signed: (model - measured) / measured.
- **Common random numbers.** Replication r of seed s draws order i, step k's work time from one fixed uniform, and bootstraps each station's samples from a stream keyed by (s, r, hash of station id). So two layouts, or 3 vs 4 workers, see the same luck; a drag never flickers. Default seed 1, 200 replications.
- **Range = p10 to p90 over replications** of the run's mean order time (each replication also resamples the measured work times, so a short run's uncertainty shows). Ranges are rounded outward when shown.
- **Prediction is fast enough to recompute per frame without caching**: resolve world + paths + 200 replications of 10 orders took about 1.5 ms on the build machine (M-series Mac).

## World and fixtures

- **The world has its own geometry, routing and randomness** (`tools/world/`). It imports only types and the three protocol constants (`HANDOFF_REACH_M`, `STAND_OFF_M`, `BODY_RADIUS_M`) from `src/core/types.ts`. Those constants are the staging instructions the real room follows too, not model parameters.
- **People walk in the true room; the model sees a noisy scan of it.** Scan centres are off by about 1 cm, sizes by about 1.5 %, yaws by up to 2 degrees. The camera adds 2 cm noise per axis, a constant calibration offset of about 1 cm, about 1 % dropped samples and one short occlusion per run.
- **Same people in every run.** Person traits (speed 1.0 to 1.3 m/s, acceleration, skill, tap delay, fumble chance, sway) come from one fixed seed; each run's own seed adds day-to-day pace variation of a few percent and all event randomness. Otherwise run B against run A would partly measure different people.
- **One scan, reused by all three runs.** A changed run differs only in `layout.json` (the fridge's placement in B, a fourth worker in C), as a drag in the product would. B's fridge placement is the true new position plus about 1 cm of hand-placement error.
- **Fridge in B is a back-bar fridge behind the Make worker** (door facing the counter, 0.4 m walk). Order, Make and Finish sit side by side on the back counter with no gap, so "next to Make" means behind the worker. The alternative, a gap in the counter line, would have made Order-to-Make a carry and made Order a second bottleneck.
- **Hand-offs and carries.** Order to Make and Make to Finish are hand passes (stand points 0.90 m apart). Finish to Pickup is a carry (1.13 m). The test checks these are not borderline: the same answer comes from the true room and from the noisy scan.
- **World tuned to make the story clear, not the model look good.** Distances and work-time medians were adjusted until A finished under 90 s with a visible queue at Make. Nothing was adjusted against the model's output.
- **The queue floor mark is in the scan as an `unknown` box, 2 cm high.** RoomPlan does not detect floor marks, so a real scan needs it added by hand (or the owner adds it in the editor). The scan noise is a `chair` (a stool in the corner) with low confidence, marked `ignore`.
- **Fixture scans say `source: "synthetic"` and have no `device`.** They look like a RoomPlan export but nobody scanned them; claiming `roomplan` would be dishonest.
- **Walls carry a thickness (about 10 cm) centred in the wall.** RoomPlan reports walls as zero-thickness planes, but our format requires `size.d > 0`. The scan app should pick a nominal thickness.
- **Collisions between people are not simulated.** In run C two people share Make and may walk to the fridge at once; their paths can overlap. With three or four people this is rare and short.
- **The validator has its own zod schemas** (`tools/world/schemas.ts`), with a compile-time drift check against `types.ts`, so it runs without the product. Unknown fields are warnings (likely typos), not errors.

## Scene

- **Look: a painted-wood diorama on a play table.** Cream tiled floor on a birch-ply board (with a "1 m" scale bar and 1 m lines), pale eucalyptus table behind it, chunky rounded blocks with a dark cartoon outline. Role colours are jade (station), lavender (storage), berry (pickup), marigold stripes (queue floor mark), stone (fixture), picked to stay clear of the red/blue/yellow/green worker hats. Tomato is reserved for "orders piling up here".
- **Labels are HTML overlays, not sprites.** Crisp at any projector resolution and use the bundled Baloo 2 font. They hang above each box's back edge so the front of the top (piles, toppers) stays visible; later tags are nudged up instead of overlapping; a tag fades to 30% when a worker's head is under it. Size follows the scene size (18–30 px), so side-by-side halves stay legible.
- **Order tickets pile on the station's top (front-right corner), not on the floor beside it.** The floor beside a station is where the worker stands and where neighbours touch; on top, the pile is never hidden and grows into a tower. At the alert size (default 4) tickets turn tomato, the station's outline turns tomato and a pulsing tomato rim appears on the floor. A count badge shows the true number (only 14 tickets are drawn).
- **The reveal shows raw scan first, then the owner's names.** During `playReveal` every box (including scan noise) is plain white with a dashed slate-blue scanner tag ("table", "storage"). `showNames` repaints by role, adds toppers and lock bolts, and shrinks away `ignore` boxes. Lock bolts appear only after naming, because the scan does not know what is locked.
- **Drag collision: footprints as axis-aligned rectangles (rotated extents), slide per axis.** If the spot under the pointer is free the item goes there (it may hop past an obstacle); otherwise it slides along the blocking face, trying both axis orders. Queue marks and ignored boxes do not block. Exact for quarter-turn yaws; conservative for other angles.
- **Framing uses the scan positions only**, so a drag never makes the camera jump. The drag area is the room bounds minus wall thickness on walled sides.
- **Workers are smoothed with a frame-rate-independent exponential filter (tau 0.14 s)** and snap on jumps over 2.5 m (a replay seek). This adds about 0.15 s of visual lag; acceptable for ~10 Hz noisy logs.
- **Pawns are drawn at 1.25x scale (~0.95 m tall)** so hats peek over 0.9 m counters. Workers standing behind a counter are still partly hidden; we keep a fixed camera rather than x-ray effects.
- **Rendering on demand**: one rAF loop per scene, rendering only when something changed or is animating; pixel ratio capped at 2.
- **2026-11-14, after the first fixture comparison missed: walking pace from whole trips, and pace uncertainty in the ranges.** Two changes were made after the first comparison put counter-b and counter-c just outside their ranges. Judge them on the reasons below, which do not depend on those numbers. Nothing was tuned to the fixtures, and the new numbers are reported whichever way they moved.
  - *Pace from trips (`trips.ts`, `pace.ts`).* The model uses speed only to turn a path length into a duration. The right quantity is therefore trip duration over modelled trip distance, which includes speeding up, turning round and reaching into the fridge. The old median of 0.5 s windows (kept in `speed.ts`) measured cruising speed instead.
    - **Finding trips.** A trip is an excursion of more than 0.5 m from the worker's own stand point, timed from the last sample within 0.25 m of home to the first one back within 0.25 m.
    - **Matching.** Each trip is matched to the fetch or carry leg whose far stand point it came within 0.5 m of; if it reached several, the longest leg wins. Its distance is that leg's round trip minus the start and end samples' distances from home.
    - **Fitting.** With two groups of at least 2 trips whose mean lengths differ by 1 m or more, we fit duration = overhead + distance / speed. The overhead is per round trip, split half each way. Otherwise, or if the fit gives a negative overhead or slope, we use one effective speed (the median of distance / duration) and add a warning. With fewer than 4 trips we fall back to the window estimator, and with no walking at all to an assumed 1.2 m/s.
    - **What this does not catch.** Any speeding up inside the 0.25 m home circle is still missed.
  - *Pace uncertainty in the ranges.* "Short runs give uncertain averages" applies to walking pace as much as to work times. Each replication now bootstraps the detected trips within each group, which keeps the length spread so the fit always exists, and refits by the same method. The pace stream is keyed by (seed, rep), so every layout sees the same pace in a given replication and a drag does not flicker. A resampled fit with a negative overhead is clamped: overhead 0, line through the origin.
  - *Staffing assumption stated.* When any station has more than one worker, the assumption text says "Two people at one station work side by side without getting in each other's way." The mechanics are unchanged.

## Server, inputs and tablet

- **One `RunFeed` interface for live and replay.** Consumers subscribe to taps and positions and never branch on `kind`. Every feed ends with exactly one `{type:"end"}` tap, so "the run is over" looks the same live and replayed.
- **Live and recorded feeds run side by side during a live run** (`createSwitchableFeed`). Failover is a filter switch, not a restart, so it is instant and continues at the current run time. Cost: the recording's timers run in the background the whole live run (cheap).
- **Failover is per input.** Camera silence (default 4 s without a sample) replaces positions only; live taps keep flowing. A closed link for 2 s replaces both. Auto-failover is on by default; the operator can switch any input back to live (`setSource`), and nothing is delivered twice.
- **Taps failover catches up.** When taps switch to the recording, recorded steps from before the switch that were never delivered are delivered at once with their recorded `t`, so no order is left with step 2 done but no step 0. These catch-up events are the one exception to "taps arrive in time order". Mixing a live run and a recording is inherently approximate; a run that failed over is labelled "(taps partly from the recording)" when saved, so it is not mistaken for a clean recording.
- **The stage stamps positions too, not only taps.** The camera's own clock (`cameraT`) is informational. Device clocks never need to agree; the cost is network latency (tens of ms on a LAN) in every sample.
- **The tablet sends unstamped `tap` messages with a `tapId`; the stage answers with the stamped `done` (which is the ack) or `tap-rejected` with a reason.** Resends are safe (same `tapId` is acked again, never counted twice). The stage rejects taps that skip a step, repeat a step or name an unknown order, so all tablets stay consistent.
- **A tap made while the tablet is offline is kept and resent on reconnect**, so it is stamped late by the length of the outage. Dropping it would lose the step entirely; the person would tap again later anyway.
- **Double taps:** after a tap, a column shows "✓ #3 done" for 0.9 s and ignores taps, so a double tap with floury fingers never finishes the next ticket.
- **Late joiners rebuild from `run-state`.** The stage sends the full event list on start, end and in reply to `sync-request` (sent by tablets on every connect). The server keeps no run state; it only relays.
- **Tablet queues are first come, first served** in the order the stage released or passed on each ticket. Tickets are labelled by schedule position ("#3"), which is what people call out.
- **Server: node:http plus `ws`, no framework.** Static files are served only via a path check that rejects `..`, encoded slashes, backslashes and NUL. Recordings are written to a temp folder then renamed, so a half-written run never appears in the list; a clashing id gets `-2`, `-3`. No CORS headers: the scan app is native and does not need them.
- **JSONL parsing sorts events by `t` (stable)** instead of rejecting out-of-order lines, so hand-edited logs still load. It does reject a second `end` or events after `end`.
- **Positions header `hz` for saved recordings defaults to 10.** Live samples arrive at whatever rate the camera page sends; `hz` is nominal and nothing computes from it.
- **`npm start` rebuilds when anything in `src/` is newer than the built pages**, tests included. A spare rebuild costs seconds; a stale build on stage costs the demo.

## Camera tracker

- **Hat colour in HSV, per frame, at 480 px wide.** A pixel belongs to a hat when its hue is within 16 degrees of the target and it is saturated and bright enough (absolute floors plus a share of the target's own saturation and value, so a sampled dull hat still matches itself). Hue survives lighting change better than RGB. 480 px keeps a frame under ~10 ms in the browser; a hat 4 m away is still about 270 px of area there.
- **Blob rules.** 8-connected regions; fragments closer than 1.6 x their summed radii are merged (an arm across a hat splits it). Smallest hat: 0.06 % of the frame (78 px at 480x270), which ignores a mug but would also lose a hat much further away than in our 4.5 x 3.5 m room. A rival blob at least 45 % of the largest makes the colour ambiguous: we keep the candidate near last frame's position if exactly one is, otherwise report nothing for that worker.
- **One-click colour sampling replaces the layout's hex.** Per worker, stored with the calibration. The layout colour is only the starting guess; the camera's view of a fabric under kitchen light is what matters.
- **Hat height is handled with a full camera model, not a floor homography alone.** Hat pixels pushed through the floor homography land metres behind the person. We recover the missing column of the 3x4 projection (the image direction of "up") from two or more clicked box-top corners whose heights the scan knows, then map each hat through the plane at that worker's hat height. Exact for a pinhole camera. Fallback with floor points only: assume a centred lens and square pixels and solve the focal length from the floor's right angles. That fallback is labelled approximate in the UI because it is fragile: for a camera facing the counter squarely, a principal point 5 px off costs about 11 cm (measured in `camera-model.test.ts`).
- **Hat heights per worker, measured by a click.** Default 1.65 m. "Measure" solves the height from one click on the hat while the worker stands on their own stand point (one linear equation). Floor error is about dh x d / (C - h): with the camera 2.8 m up and people about 4 m away, 1 cm of hat height is 3 to 4 cm on the floor. On the synthetic video, the 1.65 m default for everyone gave a 10 cm mean error; measured heights gave 3 cm.
- **Calibration errors are shown per point, plus one "suspect".** In-sample errors spread one bad click over every point, and leave-one-out flags far corner points instead of the bad one. So we flag the point whose removal makes all the others fit at least twice as well (and that is over 5 cm off by itself).
- **Smoothing: alpha-beta (constant velocity) filter, alpha 0.6, beta 0.25, speed clamp 2.5 m/s.** Plain exponential smoothing with tau 0.12 s lagged a walking person by about 14 cm on the synthetic video; the alpha-beta filter has no steady lag. A jump over 0.9 m must be seen in two frames running before the dot moves there.
- **Gaps: hold the last position up to 0.5 s, live only.** Held positions keep the stage's dots steady through a brief occlusion, but they are stale (up to ~45 cm for someone walking past the lamp), so they are never written to a recorded `positions.jsonl`, which keeps only fresh sightings (the format allows gaps). After a hold the next sighting snaps rather than being smoothed in from the stale point. Past 0.5 s we send nothing for that worker; the stage's watchdog handles silence.
- **Positions outside the room (by more than 0.5 m) are rejected** as false detections.
- **Reports at 10 Hz, only for tracked workers; frames are processed at up to 30 per second.** A timer drives the loop, not requestAnimationFrame, because rAF stops when the window is covered (the stage window on top). A hidden tab still slows down; the page warns.
- **Calibration stored per camera (its label, or the video's file name) and per scan** (`capturedAt` and box/wall ids), not per layout: dragging a box on the stage moves the box outlines but not the floor. Pixel coordinates are rescaled if the camera delivers a different resolution. Export/import as JSON.
- **The kitchen comes from the stage's `kitchen` message; a recorded run can stand in** when no stage is open (rehearsal, filmed video).
- **Whole-file processing seeks the video in 0.1 s steps of video time** and stamps samples with video time. Seeking is exact and independent of the laptop's speed; it is slower than playing for videos with sparse keyframes (phone videos), which we accept for an offline step.
- **Synthetic camera for testing, our own software renderer** (`tools/camera/`): fixture positions drawn by a pinhole camera 2.8 m up with a slightly off-centre lens, shaded boxes, people with hats at 1.63 to 1.70 m, a pendant lamp that hides a hat, a raised arm every 17 s, a red mug, brightness swing, blur, noise, VP8/H.264 compression. Simple shapes, so it tests the geometry and the pipeline honestly but flatters colour detection (round, evenly coloured hats).

## Stage app

- **Layout: the kitchen fills the screen left of one paper rail.** The rail holds the step's words and at most two big numbers; charts (the trust pairs) are small and live in the rail, never over the model. Panels copy the scene's sticker look (paper, thick ink outline, hard offset shadow) so the screen reads as one toy, not a dashboard beside a toy.
- **Keyboard map:** → / Space / PageDown next, ← / PageUp back, 1–6 jump, P play / play again / start a live run / replay the scan, F faster (4x), E skip to end (ends a live run), I inputs drawer, Esc close, M and W the two rehearsed changes, Backspace reset Play, S retry saving. Keys typed into a text field are ignored. P does nothing while a live run is running, so a live run can never be restarted by accident.
- **URL params:** `run` (base run id, default counter-a), `mode=replay|live` (live starts all three inputs live), `speed` (0.25–64, every replay and the Compare clock), `step` (1–6 to open on). Unknown values fall back to the defaults.
- **The prediction is frozen on leaving Play, for the judge's layout and for every recorded second run's layout**, all from the first run's calibration (`app/frozen.ts`, whose input type has no place for a second run's logs). If the judge's layout matches no recording, Test switches the layout shown and the compared prediction to the nearest recorded run's layout, says so plainly, and never compares a prediction for one layout with a run of another.
- **Matching the judge's layout to a recorded run:** every box within 0.45 m of the recorded spot, and the stand point of every station, storage and pickup within 0.45 m (a fridge in the right place but facing the wrong way is a different walk, so it does not match), and the same number of workers at each station. 0.45 m was chosen as "about one body width" before looking at any result; the rehearsed shortcuts (M, W) set the layout to the recorded layout exactly.
- **Test shows the unrounded edges next to the rounded range** ("Predicted 8–10 s (8.8–9.7 s before rounding). Measured 9.9 s."). Ranges are rounded outward for display (core rule), so a measured 9.9 s looks inside "8–10 s" while it is outside 8.8–9.7; without the exact edges the verdict would look wrong. A miss under 5% of the range edge is "Just outside"; more is "Outside". Both give the seconds and the direction.
- **The verdict appears only when the second run has played to its end** (or was skipped to the end), even though a recording's result is known at once. The room sees the run before the answer.
- **Measured means show one decimal ("9.9 s")**; predicted ranges use the core's whole-second, outward rounding.
- **Run story:** "Orders waited longest at X: N s each on average, up to K at once." X is the station with the longest mean time from an item's arrival to its step being done (waiting plus work), from the tap log; K is `peakQueue`.
- **Pile alert at 3 tickets on the stage (scene default 4).** On counter-a the Make pile sits at 2–3 for most of the run and reaches 4 only briefly; at 3 the slow station glows for most of the middle of the run, the others never do.
- **A run belongs to a kitchen.** A recorded or live run is used for Trust and Play only while every station, storage and pickup of the kitchen it was made in is still in the current scan. Renames, floor marks and splits keep it; a fresh phone scan does not, and the screen says "This kitchen has not been run yet" instead of reading one kitchen's taps in another.
- **Dragging in the Scan step** is on for a live scan (the owner puts things where they really are) and after adding a floor mark; off for a recorded scan, so a stray drag cannot move a box away from where its recorded run happened.
- **Starter setup for a live scan** (`app/starter-setup.ts`): tables, cabinets ("storage") and counters are counters; left to right they are stations, the right-most is the pickup; refrigerator → storage; sink, stove, oven, dishwasher → fixed and locked; under 6 cm tall → queue floor mark; chairs and other furniture, and anything with low confidence → hidden. Stand side faces the middle of the room. On the counter-a scan this reproduces the staged setup's roles and route exactly. The schedule is 10 orders, first at 1.5 s, then every 6 s ± 1 s from a fixed seed.
- **Live versus recorded per input.** A run with taps and positions both recorded is a plain replay (speed and skip work). A run with either live is a switchable feed with the recording standing by; switching an input in the drawer applies at once during such a run and at the next run otherwise (the drawer says so). A failed input stays on the recording for the next run too, until switched back.
- **No tablet connected for 5 s during a live run → the recorded taps take over.** The input layer deliberately never judges taps by silence (a slow station is quiet), but zero tablets connected means nobody can tap; without this a run with no tablet would never end.
- **Saving a live run** retries three times (0, 1, 3 s), then keeps the run on screen and offers S to try again. Recordings that used the recording for any input carry the input layer's "(… partly from the recording)" title.
- **Compare plays one simulated run per side** (`simulateRun`, seed 1, replication 0, the same for both), labelled as such, with each side's exact walking and simulated range beneath. It is one draw, not the range: the range is the number to quote.
- **Compare uses a more frontal, higher camera** (azimuth 0.14, elevation 1.06) than the main view, so each half-screen is filled top to bottom instead of leaving bands; the scene got a `view` option for this.
- **Scene changes:** the bottleneck halo is now a soft glowing ring texture rather than a flat slab; each pawn has a see-through cap (depth test "greater") that shows only where a counter hides the real cap; the "Fixed: power" hint draws above the name tags; tickets are 20% larger.
- **2026-11-14, after an independent review: four defects fixed.**
  - **Trips are timed from rest to rest.** Each trip now runs from the last moment at rest at home to the first moment at rest back home. It is paired with the full modelled round trip, with no trimming, so the cost of starting and stopping lands in the fixed overhead.
    - "At rest" means the speed over ±2 samples of the 5-sample running-median positions is below 0.12 m/s.
    - For a physical start (speeding up from rest at about 1.5 m/s²), this finds the moment of departure to within one 10 Hz sample.
    - A start that is instant (the simulator's own animation trace) is read about 0.2 s early at each end.
  - **Home is each worker's own resting place.** It is the median of where they stood still within 1 m of their station's stand point, not the stand point itself. Two people sharing a station rest either side of it.
  - **Extrapolation is stated and widens the range.** A walk shorter or longer than every measured trip (with 0.05 m tolerance) is named in `Prediction.extrapolation` and in the assumption text.
    - In that case each replication draws its pace model 50/50 from the bootstrapped overhead + speed fit and the bootstrapped single effective speed. Both are defensible from run A alone.
    - The draw uses a random stream keyed only by seed and replication, so a drag does not flicker. Inside the measured range the calibrated method is used alone, so the range can step wider as a drag crosses the boundary. That is deliberate.
  - **The trust check reports more alongside the headline.** The headline is still the pre-registered even/odd order-time error. It now also reports:
    - `baselineErrorPct`: every held-out order guessed at the learned orders' mean.
    - `walkCheck`: leave-one-trip-out mean absolute error, plus leave-one-group-out per kind of walk. With two kinds of walk, the leave-one-trip-out part only sees scatter about the pace model; the per-group part is the test of a new walk length.
    - `scope`: a sentence saying what the check covers.
  - `checkPrediction` has `missText`, which never says "0.0 s".
- **2026-11-14: counter-b and counter-c are no longer clean test data.** They have now been looked at repeatedly while the model was changed: three comparisons, two rounds of model changes. Their match to the predictions is no longer evidence. From here on the check is `npx tsx tools/coverage/coverage.ts 40`, which uses fresh generator seeds unrelated to the fixture seeds and predicts each changed run from its own original.
